# Candidate, review, and verdict

This is the disclosed `candidate-and-verdict` card. Read it completely after
the Lead core's manifest check and before recording a candidate, verification,
review, Human decision request, verdict, or finish.

## 1. Freeze an exact candidate

Prefer a commit when authority permits. Otherwise record a deterministic
identity containing accepted base commit, binary-safe diff digest, untracked-
artifact manifest and digests, and any generated-artifact digest. A file list
or working tree description is not an identity. Freeze the candidate during
verification and review; every candidate write creates a new identity and
invalidates earlier verification and review.

The Engineer proves writes. A fresh Reviewer falsifies the exact candidate when
the protocol or risk requires independence. The Lead inspects the artifact,
scope, commands/results, report evidence, unresolved findings, and authority,
then binds the project verdict. Re-run proportionate checks when evidence is
missing, stale, or below the protocol's risk threshold. Lifecycle state,
successful exit, and passing tests are attention signals rather than verdicts.

Candidate preparation is complete when one immutable identity covers every
changed or generated byte, its accepted base and owner are explicit, required
verification is bound to that identity, and the workspace is frozen for review.

## 2. Preserve the semantic decision chain

Append one JSON object per grounded milestone to `events.jsonl`. Every object
has `schema_version: 1`, UTC RFC3339 `timestamp`, exact `run_id`, allowed `type`,
`actor`, and event-specific evidence references. Write the full Markdown
record first and reference its relative path and SHA-256; JSONL never truncates
candidate, verification, risk, or decision information.

Allowed types and required evidence are:

- `launch`: agent, pane, recipe, context path, and digest; Launcher-owned and
  already present before handoff;
- `assignment`: assignee, disposition, Assignment path/digest, and owned scope;
- `report`: reporter, outcome/request, complete report path/digest;
- `candidate`: task and exact immutable identity;
- `verification`: exact candidate, command, cwd, result, and full evidence path;
- `review`: exact candidate, fresh Reviewer identity, decision/findings, and
  report path;
- `human_decision_request`: exact open question, authority boundary, and
  options/evidence path;
- `verdict`: exact candidate, decision, authority, unresolved findings,
  residual risks, and evidence paths; and
- `finish`: terminal project outcome and durable report/verdict references.

Example shape:

```json
{"schema_version":1,"timestamp":"<UTC RFC3339>","run_id":"<id>","type":"candidate","actor":"<lead>","task_id":"<id>","candidate":"<exact identity>","evidence":["<relative run path>"]}
```

The ledger records facts already grounded in Herdr, Git, and the filesystem. It
is not live status, a queue, a retry system, semantic parentage, or automatic
acceptance. The Launcher writes only `launch`; after the handoff marker, the
Lead is the sole appender. Event type order must match the actual decision
chain.

A Human decision request is an open request, not a decision event. Save the
Human response as durable Markdown and reference it from the next applicable
milestone or verdict. A resolvable request pauses the run without `finish`.
After `finish`, no later event is valid.

Ledger evidence is complete when every milestone is already true outside the
ledger, every referenced regular file and digest verifies, the exact candidate
is consistent across verification/review/verdict, and the sequence contains no
invented status or event type.

## 3. Decide with the owning authority

Reconcile disagreement through inspectable evidence. Route correctable findings
to the same Engineer that owns the moving scope; freeze and independently
review the new candidate. Scope expansion remains a proposal until its owner
approves it. After two materially identical failures, investigate shared
prerequisite, quota, authentication, authority, or mechanism before another
attempt.

Escalate product, portfolio, irreversible, external-effect, publication,
material-cost, and protocol-change decisions to the Human. Record their exact
decision and boundary. A Supervisor recommendation remains observation evidence
and has no project acceptance authority.

Issue one project verdict containing candidate identity, verification evidence,
required independent review and its disposition, unresolved findings, residual
risk, and the role whose authority binds the decision. Append `finish` only
after that verdict is durable and the terminal outcome has no pending resumable
Human decision.

The run is complete when the exact final candidate, all protocol-required
verification and independent review, project verdict, authority, unresolved
risk, durable artifacts/digests, and terminal ledger sequence agree. Any one
missing link keeps the run open or `BLOCKED`.
